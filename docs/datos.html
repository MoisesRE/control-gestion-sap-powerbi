Modelo de datos

Cómo se guardan los datos para que no puedan descuadrar

Buena parte de lo que en otros proyectos se revisa después, aquí está declarado en la propia base de datos, donde no se puede incumplir. Una carga que rompa una regla es rechazada en lugar de entrar y descuadrar el resultado en silencio.

El modelo

Dos tablas de hechos y cuatro dimensiones

Cada hecho se cruza con escenario, periodo, centro y cuenta. El detalle y el comparativo viven separados a propósito.

El esquema

Dos tablas de hechos, y no una. El real observado tiene grano de apunte contable; el presupuesto y el escenario generado, de centro por cuenta y mes. Apilarlos mezclaría dos granos y obligaría a cada medida a saber de qué escenario viene la fila antes de sumarla.

El real aparece en las dos tablas, y un control comprueba que ambas suman lo mismo al céntimo. En Power BI esa duplicidad tiene una consecuencia que no perdona: una medida que sume las dos cuenta el real dos veces, y por eso el modelo lleva una medida dedicada a vigilarlo.

Las reglas de negocio viven dentro de la base, no en un manual

Al crear las tablas se declara qué combinación identifica a cada fila —escenario, periodo, centro y cuenta—, de modo que una carga que duplicase una de ellas es rechazada en lugar de inflar el resultado. Y cada referencia tiene que existir: un centro de coste que no esté dado de alta no puede entrar. Es el error que en un informe aparece como una fila en blanco y descuadra los totales sin avisar.

sql/02_tablas.sqlSQL
CREATE TABLE IF NOT EXISTS core.fact_escenario (
    escenario_clave text           NOT NULL,
    fecha_clave     integer        NOT NULL,
    ejercicio       smallint       NOT NULL,
    periodo         smallint       NOT NULL,
    ceco_codigo     text           NOT NULL,
    cuenta_codigo   text           NOT NULL,
    importe         numeric(18, 2) NOT NULL,
    CONSTRAINT fact_escenario_pk PRIMARY KEY
        (escenario_clave, fecha_clave, ceco_codigo, cuenta_codigo),
    CONSTRAINT fact_escenario_escenario_fk FOREIGN KEY (escenario_clave)
        REFERENCES core.dim_escenario (escenario_clave),
    CONSTRAINT fact_escenario_tiempo_fk    FOREIGN KEY (fecha_clave)
        REFERENCES core.dim_tiempo (fecha_clave),
    CONSTRAINT fact_escenario_centro_fk    FOREIGN KEY (ceco_codigo)
        REFERENCES core.dim_centro (ceco_codigo),
    CONSTRAINT fact_escenario_cuenta_fk    FOREIGN KEY (cuenta_codigo)
        REFERENCES core.dim_cuenta (cuenta_codigo),
    CONSTRAINT fact_escenario_clave_derivada
        CHECK (fecha_clave = ejercicio * 100 + periodo)
);

Una regla impide cargar datos sin anonimizar

La base exige que todo código de centro tenga la forma del pseudónimo. Si alguien cargara por error el extracto original en una base destinada a publicarse, fallaría en la primera fila y no en la revisión final.

sql/02_tablas.sqlSQL
CONSTRAINT dim_centro_codigo_pseudonimizado
    CHECK (ceco_codigo ~ '^CC-[0-9]+$')

Decimales exactos, no aproximados

La suma en coma flotante no es asociativa, de modo que el total de una columna dependería del orden en que el planificador decidiese agregar las filas: el mismo SELECT podría devolver dos céntimos distintos entre ejecuciones. Al volumen del detalle la deriva aparece de verdad: 428.589 importes suman ...,7299999 en lugar de ...,73.

Las vistas del P&L

Seis vistas reconstruyen la cuenta de resultados. Son vistas y no tablas materializadas: a este volumen, materializar añadiría un REFRESH que orquestar tras cada carga y la posibilidad de servir una versión desincronizada, a cambio de ahorrar décimas de segundo.

Tiempo de ejecución, mediana de siete pasadas con caché caliente

El convenio de signo hace el trabajo. Los importes conservan el signo de SAP, ingreso positivo y coste negativo, lo que convierte tres cálculos en sumas directas: el resultado es sum(importe) sin un solo condicional. La desviación es real - presupuesto, y es favorable cuando sale positiva tanto en ingresos como en costes.

sql/05_vistas_qa.sqlSQL
-- Misma regla que la etapa 1: escalar y redondear n importes puede
-- desviar su suma hasta n medias centesimas, de modo que la tolerancia
-- es funcion del numero de filas agregadas y no un umbral elegido a
-- ojo. El suelo de 0,05 cubre los periodos con muy pocas filas.
greatest(0.05, coalesce(m.filas_agregadas, 0) * 0.005) AS tolerancia
...
SELECT * FROM comparacion
WHERE abs(diferencia) > tolerancia;

Las comprobaciones que vigilan el modelo

Por convenio, una vista qa.v_control_* devuelve cero filas cuando el modelo está sano: cada fila es un descuadre. El verificador las descubre en el catálogo en lugar de listarlas, de modo que añadir un control al DDL basta para que se ejecute, sin tocar una línea de Python.

src/finanzas_etl/load/postgres.pyPython
cur.execute("""
    SELECT table_name
    FROM information_schema.views
    WHERE table_schema = 'qa' AND table_name LIKE 'v\\_control\\_%'
    ORDER BY table_name
""")
vistas = [fila[0] for fila in cur.fetchall()]
if not vistas:
    raise RuntimeError(
        "no se encontro ninguna vista qa.v_control_*; el DDL no se aplico"
    )

No hay vista de claves huérfanas, y la ausencia es deliberada. Con las claves foráneas declaradas, una fila huérfana no puede existir, y una vista que las buscase sería incapaz de devolver una sola fila. Un control que no puede fallar no es un control.

Las pruebas que cubren estos controles no comprueban que pasen con el modelo sano, que es lo facil: rompen el modelo a propósito -- alteran un importe, declaran mal los periodos cubiertos, insertan un periodo de otro ejercicio -- y comprueban que cada control lo detecta. Todo dentro de una transacción que se deshace.

Acelerar las consultas: cuándo compensa y cuándo no

Solo se indexa la tabla de detalle. Las dos últimas filas son la razón de no indexar la tabla comparativa: con 42.017 filas la consulta ya responde en milisegundos sin ayuda, y un índice solo añadiría espacio y tiempo de carga.

Una consulta de ejemplo

Así se compone el estado de resultados oficial desde el esquema en estrella. El orden de los CASE importa: los grupos con línea propia se resuelven primero y solo lo que queda se reparte entre coste y gasto, de modo que ninguna cuenta cae en dos líneas ni se queda sin ninguna.

scripts/generar_cifras_web.pySQL
SELECT f.escenario_clave,
       t.ejercicio,
       t.periodo,
       CASE
           WHEN c.grupo = 'Ingresos'                                 THEN 1
           WHEN c.grupo IN ('Ingresos Diversos', 'Egresos Diversos') THEN 5
           WHEN c.grupo = 'Depreciacion'                             THEN 4
           WHEN c.grupo = 'Gasto Financiero'                         THEN 6
           WHEN c.grupo = 'Diferencia de Cambio'                     THEN 7
           WHEN c.clase_costo_gasto = 'COSTO'                        THEN 2
           ELSE 3
       END AS orden,
       sum(f.importe) AS importe
  FROM core.fact_escenario f
  JOIN core.dim_tiempo  t ON t.fecha_clave   = f.fecha_clave
  JOIN core.dim_cuenta  c ON c.cuenta_codigo = f.cuenta_codigo
 GROUP BY 1, 2, 3, 4

Esas siete líneas son las que el estado de resultados de la portada compone en treinta y una filas. Su suma es el resultado neto al céntimo, y una prueba lo comprueba en los cuatro escenarios.
